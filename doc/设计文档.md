## 1. 概述

### 1.1 背景与目标

商户（SaaS 平台、电商、服务商等）在接入支付时，往往需要分别对接微信、支付宝、中金支付、宝付支付等多个第三方支付通道。每个通道有独立的 API、认证方式、费率结构、额度限制、回调机制，导致：

- 商户集成成本高、周期长
- 多通道管理复杂，运营负担重
- 某一通道异常时缺乏自动容错能力
- 新通道接入需要代码开发，扩展性差

**本平台旨在**：构建一个支付通道聚合与适配层，通过统一接口、策略驱动路由、可插拔通道接入，让商户以最小成本获得多通道支付能力，并实现智能容错与用户无感授权。

### 1.2 核心价值

| 价值维度 | 说明 |
|---------|------|
| 统一接入 | 商户通过一个 API 即可调用所有已接通道 |
| 策略路由 | 根据费率、额度、场景、风控等规则动态选通道 |
| 用户无感容错 | 通道异常时自动切换至预授权的备用通道 |
| 配置化扩展 | 新通道接入仅需配置，无需编写业务代码 |
| 数据统一 | 所有渠道的订单、交易、对账数据汇聚到统一视图 |

## 2. 术语定义

| 术语 | 定义 |
|------|------|
| **支付通道 (Channel)** | 第三方支付提供方，如微信支付、支付宝、中金支付、宝付支付等 |
| **商户 (Merchant)** | 使用本平台提供支付服务的商业实体 |
| **应用 (App)** | 商户在平台创建的支付应用实体，拥有唯一 `appid` |
| **渠道实例 (Channel Instance)** | 某一支付通道在某个应用下的具体配置（含密钥、费率、额度等） |
| **支付策略 (Payment Strategy)** | 应用级或订单级的路由规则，决定使用哪些通道、优先级、条件 |
| **用户授权 (User Authorization)** | 支付发起方（终端用户）对特定支付通道的授权凭证 |
| **综合授权 (Comprehensive Authorization)** | 用户一次性授权商户所配置的所有支付通道，实现后续无感切换 |
| **路由引擎 (Routing Engine)** | 根据策略和实时通道状态，动态选择支付通道的核心服务 |
| **通道适配器 (Channel Adapter)** | 封装特定支付通道 API 调用的可插拔模块 |
| **交易 (Transaction)** | 支付、退款、查询、回退等操作的统称 |

### 3.2 架构特性

- **分层清晰**：接入层 → 业务服务层 → 适配层 → 第三方通道
- **适配器模式**：每个支付通道实现统一的 `IPaymentChannel` 接口，业务层不感知具体通道
- **配置驱动**：通道接入参数、策略规则均存储于数据库，新增通道无需代码改动
- **无状态路由**：路由引擎基于策略 + 通道实时状态决定路由，易于水平扩展

## 4. 核心流程

### 4.1 商户接入流程

```
商户注册 → 实名认证 → 创建应用 → 获取 appid
                                              ↓
                                  选择支付通道（多选）
                                              ↓
                                  配置渠道实例（密钥、参数）
                                              ↓
                                  配置支付策略（费率、额度、场景、风控）
                                              ↓
                                  发布策略 → 应用生效
```

### 4.2 终端用户支付流程（含无感容错）

```
用户发起支付请求
        ↓
[路由引擎] 根据策略选择最佳通道 A
        ↓
[授权检查] 用户是否已授权通道 A？
   ├── 已授权 → 直接调用通道 A 支付
   └── 未授权 → 引导用户进行「综合授权」
        ↓
[支付执行] 调用通道 A 支付 API
        ↓
   通道 A 成功？ → 返回成功，记录渠道绑定
        ↓ 失败/异常
[容错逻辑] 通道 A 不可用
        ↓
[路由引擎] 从策略的候选通道列表中选择下一个通道 B
        ↓
[授权检查] 用户是否已授权通道 B？
   ├── 已授权（综合授权已涵盖） → 无感切换，调用通道 B
   └── 未授权 → 引导用户补充授权（或根据策略容错等级决定）
        ↓
[支付执行] 调用通道 B 支付 API
        ↓
   通道 B 成功？ → 返回成功，记录渠道绑定
        ↓ 失败
[进一步容错] 继续遍历候选通道，直至全部耗尽 → 返回支付失败
```

### 4.3 退款流程

```
退款请求 → 查询原始交易记录 → 获取原始支付通道
        ↓
[退款路由] 优先使用原始通道执行退款
        ↓
   原始通道可用？ → 调用退款 API
        ↓ 失败
[容错] 尝试其他已授权通道退款（需考虑不同通道的退款兼容性）
```

### 4.4 对账与Reconciliation流程

```
每日定时触发 → 遍历所有交易记录 → 逐一调用对应通道的查询API
        ↓
比较平台记录与第三方记录 → 生成差异报告 → 商户审核处理
```

## 5. 关键设计决策

### 5.1 综合授权设计（核心）

#### 问题
用户首次支付时选择通道 A，后续如果 A 不可用，需要切换到 B，但用户尚未授权 B，导致必须再次授权，体验差。

#### 解决方案：一次性综合授权

在用户首次支付时（或在商户设置阶段），引导用户完成 **对该应用所配置的所有支付通道的综合授权**。具体方式：

**方式一：前置综合授权（推荐）**

- 用户首次在商户应用下发起支付时，弹出统一授权弹窗
- 列出该应用已配置的所有支付通道（微信、支付宝、中金、宝付等）
- 用户勾选/确认后，一次性取得各通道的授权凭证（或授权令牌）
- 后端将各通道的授权状态与用户标识绑定，并存储
- 後续任何通道切换均无需用户再次操作

**方式二：平台托管授权**

- 用户仅向本平台授权一次（登录/绑定），平台作为委托代理人持有各通道的支付权限
- 各通道的具体授权由平台在后台完成（通过平台与各通道的商务授权）
- 用户侧无感知，平台侧需要与各通道签订代理授权协议

**方式三：渐进式授权 + 缓存**

- 用户第一笔支付时选择通道 A，授权 A
- 平台在后台自动尝试获取 B 的授权（若通道支持无感授权或令牌交换）
- 若自动获取失败，则在 A 故障时提示用户快速授权 B

#### 推荐组合

- **主流程**：方式一（综合授权）—— 用户体验清晰，技术实现确定
- **增强**：方式二（平台托管）—— 对于已经与平台签约的商户，可提供更高等级的无感服务
- **降级**：方式三（渐进式）—— 作为兼容方案，用于部分不支持综合授权的通道

### 5.2 策略路由设计

路由引擎根据以下维度决定通道选择：

| 维度 | 说明 | 示例 |
|------|------|------|
| **订单金额** | 按金额区段选择不同通道 | <100 元走微信，100-1000 元走支付宝，>1000 元走中金 |
| **费率** | 按费率优先级排序 | 渠道费率越低优先级越高 |
| **场景** | 根据支付场景匹配通道能力 | 直播打赏走宝付，电商交易走微信/支付宝 |
| **地域** | 根据用户 IP/归属地选择 | 某地区某渠道成功率更高 |
| **设备/客户端** | 根据终端类型路由 | App 内 H5 走微信 JSAPI，小程序走小程序支付 |
| **风控等级** | 高风险订单走更严格的渠道 | 特定渠道启用额外验证 |
| **通道状态** | 实时健康检查，跳过不可用通道 | 通道 API 超时/卡顿则降权 |

策略配置示例（JSON）：

```json
{
  "appid": "app_xxx",
  "strategy_name": "电商默认策略",
  "rules": [
    {
      "priority": 1,
      "name": "低金额微信优先",
      "condition": { "amount_range": [0, 100], "scene": "ecommerce" },
      "channels": ["wx_jsapi", "alipay_trade"],
      "sort_by": "fee_rate_asc"
    },
    {
      "priority": 2,
      "name": "中高金额支付宝优先",
      "condition": { "amount_range": [100, 10000], "scene": "ecommerce" },
      "channels": ["alipay_trade", "wx_jsapi", "zj_payment"],
      "sort_by": "fee_rate_asc"
    },
    {
      "priority": 3,
      "name": "大额中金支付",
      "condition": { "amount_range": [10000, null], "scene": "ecommerce" },
      "channels": ["zj_payment", "alipay_trade"],
      "sort_by": "limit_first"
    }
  ],
  "fallback_policy": {
    "enabled": true,
    "max_attempts": 3,
    "require_re_authorization": false
  }
}
```

### 5.3 通道插件化设计

#### 统一接口定义

```java
public interface IPaymentChannel {
    /** 通道元信息 */
    ChannelMeta getMeta();

    /** 创建支付订单（返回第三方订单号或预支付编号） */
    ChannelOrder createOrder(PaymentRequest request);

    /** 执行支付（对于需要跳转/唤起的渠道，返回跳转信息） */
    PaymentResult pay(ChannelOrder order, PaymentContext context);

    /** 查询订单状态 */
    TransactionQuery queryOrder(String thirdOrderId);

    /** 退款 */
    RefundResult refund(RefundRequest request);

    /** 交易撤销（仅适用于部分渠道） */
    boolean cancel(String thirdOrderId);

    /** 回调通知验证 */
    boolean verifyCallback(Map<String, String> callbackParams);

    /** 获取渠道健康状态 */
    ChannelHealth getHealth();
}
```

#### 配置化加载

每个通道适配器的配置存储在数据库 `channel_config` 表中，平台启动时加载所有已启用的适配器实例：

```json
{
  "channel_code": "wx_jsapi",
  "channel_name": "微信支付 JSAPI",
  "adapter_class": "com.pay.channel.wechat.WeChatJSAPIAdapter",
  "config": {
    "appid": "wx1234567890",
    "secret": "***",
    "mch_id": "1234567890",
    "cert_path": "/path/to/cert.pem",
    "key_path": "/path/to/key.pem",
    "rate": 0.006,
    "max_amount": 50000,
    "scenes": ["ecommerce", "live", "app"]
  }
}
```

新增通道时：
1. 编写适配器类（实现 `IPaymentChannel`）并打包
2. 在平台后台添加通道配置（指向适配器类）
3. 平台动态加载，无需重启（或热加载）

#### 适配器注册机制

- 使用 Java SPI 或 Spring 的 `ApplicationContext` 自动扫描注册
- 配合配置中心，运行时可动态增删适配器实例
- 每个实例与一个 `channel_code` 唯一绑定

## 6. 数据库模型（ER 概要）

详见 `ER模型.md`。

核心实体：

- **merchant**（商户）
- **app**（应用，属商户）
- **channel_config**（渠道实例配置，属应用）
- **payment_strategy**（支付策略，属应用）
- **strategy_rule**（策略规则，属策略）
- **user_auth**（用户对渠道的授权记录）
- **transaction**（交易记录）
- **channel_binding**（用户与渠道的绑定关系）
- **callback_record**（回调记录）
- **reconciliation_task**（对账任务）

## 7. API 接口概要

详见 `API接口文档.md`。

分组：

- **商户/应用管理**：注册、认证、创建应用、管理渠道、策略
- **支付接口**：创建订单、支付执行、查询、退款、撤销

- **对账接口**：对账请求、差异查询、对账报告
- **管理接口**：渠道健康监控、配置发布、统计
